## Settlement identity and cutover

The running v32 release and the proposed V2 port both use numeric verifier slot 8. The server maps this slot to one app-bound key. The deployed dual router has one PLONK target for that slot, and governance can rotate it. Existing in-flight proofs belong to the old key. For the current testnet, drain and execute outstanding ranges at a recorded common boundary before switching the server, workers and Gateway/root verifier registrations. A fresh network can start directly with its final guest identity. The current EVM receipts cover the corrected testnet guest with the proposed production-mode router on isolated Prague EVM; retained-guest receipts are historical comparisons. Any further change to the guest, including an alternate streaming verifier or different compiled mainnet address/domain configuration, requires its matching commitment and verification key. ## Proving performance

The Syscoin v32 worker produces per-batch FRI proofs. The range worker merges consecutive FRI proofs, performs RISC wrapping and compression, and produces the final PLONK SNARK. Per-batch proving can be distributed. The final wrap depends on the completed range.

The comparison uses the released worker and the candidate on the same RTX 5090 with the same two contiguous native witnesses, Security100, and matching app-bound keys. Measurements track cold setup, warm FRI, range merge, RISC wrapping, compression, and final PLONK, along with process peak RSS and sampled GPU occupancy. These two minimal batches are a compatibility and latency workload. Sustained production throughput requires a representative transaction mix.

### 8 GiB worker limit

With 8,588,361,728 device bytes available on the RTX 5090, the V2 SNARK worker reserved 7,980,711,936 bytes and failed in RISC setup before accepting a job. One request required 35,713 blocks of 262,144 bytes, or 8.719 GiB, before other live buffers. The request comes from sorting and scanning the RISC circuit’s 585,105,408 copy-permutation cells. The live index, result and scratch buffers alone require about 15.26 GiB in this implementation. CPU merging alone leaves this independent wrapper allocation in place. [Boojum CUDA workspace calculation](https://github.com/syscoin/zksync-protocol/blob/3c3472d93611bafcdadf928829cc3fb357c6b156/crypto-gpu/crates/boojum-cuda/src/ops_complex.rs#L554-L579) · [Shivini setup allocation](https://github.com/syscoin/zksync-protocol/blob/3c3472d93611bafcdadf928829cc3fb357c6b156/crypto-gpu/crates/shivini/src/cs/setup.rs#L275-L287) The experiment limited available memory on the same card. An actual 8 GiB model could have different timings.

The CLI independently verified the CPU-combined result. Feeding that result directly to the GPU RISC wrapper under the same memory cap failed in the same permutation-column setup allocation after 152.40 s. The call stack identified the request before compression or final PLONK. This isolates the device limit from the combiner.

### Streaming FRI verifier queries

Airbender #6 was closed without adoption on 2026-11-18. Its remote branch remains available at `48c998a41b2d7894bfc34968040f57b0cf7437e1`; it is not an ancestor of the selected Airbender #9 source. The measurements below remain as evidence for the decision.

The experimental verifier authenticates each opening against its committed Merkle caps, compares its index to the Fiat–Shamir transcript and completes its FRI folds before reusing the query storage. The Security100 query count and transcript inputs are the same. In RV32 replays, each workload consumed every oracle word and matched all 16 native result registers.
