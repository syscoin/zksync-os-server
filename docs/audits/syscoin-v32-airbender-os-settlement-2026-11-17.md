# Syscoin v32 Airbender, OS and settlement review

November 17, 2026. **Keep v32 on testnet.** The reviewed code binds the proof to the Syscoin guest and the batch statement. The mainnet launch profile still needs distinct signing domains, an execution-parity correction or qualification, a verifier input correction, and end-to-end evidence for the final deployment.

The implementation and qualification work that followed this static review is recorded in the [V2 port ledger](syscoin-v32-v2-port-2026-11-17.md). The public V2 port, reserved-word router correction and new testnet-guest key now have real GPU proofs and isolated EVM acceptance. The separately corrected OS guest has a different application identity. The deployment-specific launch findings below still require evidence against the chosen mainnet configuration.

### Gateway interop and the smaller upstream wrapper

Matter Labs' v33.2 atomic interop requires direct L1 settlement and v33 or newer on every participating chain. Its `AtomicFlowManager` validates the L1 chain ID on append, finality and refund. Syscoin's compact-DA route requires the edge to settle on Gateway, with Gateway settling on NEVM. Its guest commits to the ordered edge DA references and the root contract checks their availability. Adopting upstream atomic interop on that route would require defining the Gateway root used for finality and refunds, and how each edge imports it. The compression circuit can be evaluated independently while preserving the Syscoin guest and batch statement. The final PLONK circuit verifies the Boojum compression proof. With Syscoin's 100-bit, zero-PoW schedule, increasing the compression extension factor from 2 to 32 would reduce FRI queries from 120 to 24. That gives the outer circuit fewer openings to verify while increasing the extension work in Boojum. The November public wrapper enables the extra 20% queries and its Boojum scheduler gives exactly 24 for this profile. The contributions of individual gate changes and exact parity with the private September release remain unverified. A port requires new app-bound intermediate and final keys and a matching generated settlement verifier. ## Findings affecting launch

**1. The mainnet launcher defaults reuse the testnet signing domains.** The shared launcher defaults to Gateway 57001 and zkSYS 57057 for both root networks. It recognizes the canonical zkSYS edge by name and ID and uses 57057 in its additional-edge inventory checks. The bridge UI independently maps 57057 to Tanenbaum and uses 123456 in its mainnet mapping. A different root L1 chain ID does not distinguish ordinary signed L2 transactions. If two funded networks use the same L2 ID, an existing signature can be valid on both wherever the relevant account state permits. Agree on distinct production Gateway and edge IDs, make them explicit in the launcher and bridge, and reject the testnet pair on mainnet. The bridge's existing number alone does not establish the intended production assignment.
