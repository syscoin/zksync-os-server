## Authorized C1 remediation

Approvals and operation IDs now bind a persistent per-account `policyEpoch`. Installation, direct policy replacement and uninstall each advance the epoch. Replacement clears the old guardian set and pending schedule; failed replacement reverts all changes atomically. The recovery action ABI, threshold validation, guardian authority, delay and post-scheduling expiration remain unchanged. No signed deadline was added: an unused approval remains valid within the same policy epoch. The accepted scope is revocation across policy changes.

Pali carries the epoch through its recovery intent, signature and pending-operation flows, checks it against fresh chain state and compares the locally calculated approval digest with the contract. Old intents without an epoch are rejected. Pending recovery state is scoped to chain/account, and a confirmed policy change clears the pending operation while preserving the replacement credential; RPC uncertainty does not discard it. Per the user's explicit instruction, no legacy module or legacy digest support is included. This wallet change targets the coordinated fresh v32 deployment.

Canonical guardian CREATE2 address: `0x8f919fc9a92da490d305054bfd862379d2760f84`. Only the guardian creation bytecode changes; the other seven Pali creation bytecodes, SLH verifier runtime hash, infrastructure version and salts are unchanged. The release build uses Solc 0.8.28, optimizer 200, viaIR, Cancun, with CBOR/bytecode metadata disabled. Explorer verification scripts derive the guardian address from compiled creation bytecode under that same profile. Existing deployed modules are immutable and have not been updated.

The saved audit regression now requires the original stale approval to fail after uninstall/reinstall and a freshly signed approval to execute after the delay. Final local validation results are recorded in the implementation follow-up below; actual v32 deployment and real `handleOps`/prover journeys remain release gates.

## Original P2 finding: recovery policy reinstall retained old consent

**Finding:** A previously signed guardian approval that was never scheduled remains acceptable after the recovery module is uninstalled and reinstalled with the same guardian set. It also has no signed deadline: the configured expiration starts only when a recovery is scheduled. The current uninstall logic revokes the one pending, scheduled operation; it cannot revoke signatures which have not yet appeared on-chain.

**Preconditions and impact:** This requires previously valid threshold guardian signatures for the exact account/module/chain/salt/execution payload, those guardians still satisfying the policy after reinstall, and later submission of that old approval. It does not allow forging guardian signatures or bypassing the recovery delay. If uninstall/reinstall is intended to revoke earlier guardian consent, that expectation is not met. Old consent can authorize account execution after the policy has been removed and recreated, with no age limit before scheduling. Recovery execution is an executor capability with arbitrary account execution, so stale consent is security relevant even though the current delay still provides a cancellation window.

Affected source references, relative to `zksync-os-server`:

- `contracts/src/pali/PaliGuardianRecoveryModule.sol:13`: signed schedule type has chain/account/module/salt/mode/payload hash, but no installation epoch or signed deadline.
- `contracts/src/pali/PaliGuardianRecoveryModule.sol:66`: installation writes configuration without a monotonically increasing policy generation.
- `contracts/src/pali/PaliGuardianRecoveryModule.sol:78`: uninstall clears current config/guardians and cancels only `_activeRecovery`.
- `contracts/src/pali/PaliGuardianRecoveryModule.sol:111`: scheduling validates the currently configured guardian set against the unchanged signed hash.
- `contracts/src/pali/PaliGuardianRecoveryModule.sol:143`: the execution/expiration clock starts at submission time.
- `contracts/src/pali/PaliGuardianRecoveryModule.sol:214`: `getRecoveryScheduleHash()` does not bind the consent to a policy generation or signing validity window.

## Verified controls and trust boundaries

- `PaliSmartAccount.sol:39` locks the implementation initializer and fixes the EntryPoint immutably. `PaliSmartAccountFactory.sol:33` validates implementation code and EntryPoint consistency; `:46` restricts deployment to EntryPoint's SenderCreator, derives CREATE2 identity from complete initialization data, and initializes atomically through the ERC1967Proxy constructor. Existing tests cover unauthorized factory callers, repeated initialization, and initialization data binding.
- `PaliSmartAccount.sol:126` restricts validator rotation to EntryPoint or the account itself. `:136` prevents removing the active validator without replacement. `:143` admits only the active validator for UserOps; `:154` uses the active installed validator for ERC-1271 through ERC-7739. Existing tests cover account/application binding and reject the legacy raw ERC-1271 signature path.
- Canonical EntryPoint computes the typed UserOp digest using its EIP-712 domain (`integration-tests/test-contracts/lib/account-abstraction/contracts/core/EntryPoint.sol:160`) and checks/updates the sender nonce (`:840`). Replay protection relies on the correctly deployed, pinned EntryPoint and distinct chain identity. A genesis reset under the same chain ID/address space is not an independent signature domain; reset/release procedures must account for that standard property.
- ECDSA validators check owner membership, threshold and duplicate signers; malformed encoded signatures return failure. Composite validation requires installed compatible child validators, catches child reverts, enforces threshold, and rejects rich validationData rather than discarding time bounds/aggregator information. Tests cover these behaviors.
- P-256 WebAuthn checks RP ID, origin, type, challenge, user presence/verification, and canonical signature shape, relying on the chain's `0x100` precompile. SLH-DSA validators bind the verifier runtime code hash at deployment, reject malformed lengths/noncanonical keys and fail closed on verifier errors.
- Installed executors and hooks are highly trusted account code. The inherited ERC-7579 execution supports delegatecall; this can modify account storage and implementation slots. There is no separate central owner/UUPS upgrade entry point in the reviewed account, but authorized execution and installed executors remain powerful. A compatible custom module's self-reported interface is not a security attestation. No separate canonical session-key permission contract was found among the reviewed Pali sources; any session limitations must be supplied and enforced by the chosen custom validator/executor.
- The wallet intentionally uses a self-funded ERC-4337 path rather than a Pali paymaster. In verified gas-tank mode it sets inner UserOp gas fees to zero so EntryPoint does not reimburse the outer submitter in native SYS (`pali-wallet/source/utils/smartAccount/account.ts:413`, background smart-account controller around `:1099` and `:1280`). It reads outer gas-payer tank credit before signing and rechecks against actual outer transaction gas before submission (`source/scripts/Background/controllers/smartAccount/index.ts:1383`, `:1417`). This still requires v32 bootloader/prover validation; wallet unit tests cannot prove correct tank accounting.

## Remaining production acceptance requirements

- Include the locally fixed guardian and matching wallet in the v32 deployment manifest, attest its deployed runtime and rerun the actual account recovery journey. The historical pre-fix address above must not be used for the fresh release.
- Treat actual deployed bytecode attestation as a release gate. The wallet readiness probe at `source/scripts/Background/controllers/smartAccount/index.ts:387` checks nonempty code rather than runtime hashes; `scripts/explorer/blockscout/check-pali-deployment.sh:61` only checks hashes when optional expected values are provided. Require the expected EntryPoint/implementation/factory/module hashes in the production manifest and attest deployed getters and code, not just presence.
- Exercise full `EntryPoint.handleOps` through v32 with each validator, deployment+first operation, signer rotation, threshold composition, recovery cancellation/execution, invalid signatures/replay/nonces, native-gas and gas-tank accounting, exhausted tank credit, and failed/reverting operations. The completed unit tests use mocks for account/EntryPoint/precompile boundaries and do not establish GPU proof parity or real network lifecycle behavior. No Pali/handleOps coverage was located in the Rust integration-test search performed; wallet E2E journeys exist but were not run against v32.
- Preserve the explicit cryptographic qualification boundary already documented in `contracts/README.md`: the limited-signature SLH-DSA-SHA2-128-24 parameter set is experimental, the proof model is not a proof of deployed Solidity/Rust/GPU equivalence, and key-usage policy lives outside the stateless verifier. The parent audit verified that [NIST SP 800-230 remains an Initial Public Draft](https://csrc.nist.gov/pubs/sp/800/230/ipd); this parameter set has a strict `2^24` signatures-per-signing-key limit and must not be described as an approved general-purpose parameter set. This sub-audit did not inspect whether the wallet's per-key usage counter is durable, atomic, or safe across backup restores, multiple devices and cloned key material: those properties are **unverified**, not findings of failure. Conformance and counter/backup/restore evidence need explicit release acceptance.

No further operational actions or transactions were performed. No authorization bypass beyond the conditional stale-consent finding was established in the reviewed paths; this bounded audit is not a comprehensive external security assessment.
